# Как контрибьютить в humanizer-ru

Спасибо, что хотите помочь. Смерженные вклады записываются в [CONTRIBUTORS.md](CONTRIBUTORS.md). Самые ценные вклады: новые подтверждённые маркеры
AI-текста, найденные ложные срабатывания и тексты для eval-корпуса.

## Настройка окружения

```bash
git clone https://github.com/ilyautov/humanizer-ru.git
cd humanizer-ru
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

## Проверки перед PR

```bash
.venv/bin/python scripts/test_markers.py     # регресс-тесты метрик
.venv/bin/python scripts/test_score.py       # регресс-тесты балла чистоты
.venv/bin/python scripts/build_release_zip.py --output dist/humanizer-ru.zip .
.venv/bin/python scripts/install_smoke.py . --zip dist/humanizer-ru.zip
.venv/bin/python scripts/install_smoke.py .  # проверка установочной поверхности
.venv/bin/python scripts/lint_skill.py       # self-test SKILL.md против собственных правил
.venv/bin/python scripts/check_examples.py   # Факт-замок в примерах «До/После» и сверка примера аудита в README со сканером
.venv/bin/python scripts/self_scan.py        # витрина против собственных HARD BANS
.venv/bin/python scripts/test_gates.py       # тесты самих гейтов
.venv/bin/python scripts/test_modern_slop.py # сканер видит текст свежих моделей
.venv/bin/python scripts/test_mining.py      # шахта паттернов на синтетическом корпусе
.venv/bin/python scripts/bump_release.py --check  # счётчики и версия во всех местах
.venv/bin/python scripts/export_web_rules.py --check  # правила сайта свежие
.venv/bin/python scripts/build_extension.py --check   # копия движка в расширении свежая
```

CI гоняет то же самое на каждый PR (`.github/workflows/ci.yml`, там же
полный список шагов).

## Путь нового маркера

Каталог признаков и сканер живут отдельно, и новый маркер проходит оба места.

1. **Каталог.** Опишите признак в `skills/humanizer-ru/references/catalog.md`:
   следующий номер, категория (буква раздела), как выглядит след нейросети,
   что с ним делать и пара «До/После» без новых фактов. Нумерацию не сдвигайте
   и пункты физически не удаляйте. `SKILL.md` меняется только если признак
   становится жёстким запретом (таблица запретов) или меняет процедуру.
2. **Сканер**, если признак можно поймать детерминированно. Бан идёт в
   `HARD_BANS`, мягкий маркер в `SCANNER` файла
   `skills/humanizer-ru/scripts/humanizer_metrics/markers.py`. Бан, законный в
   отдельном регистре, добавляется ещё и в `GENRE_MUTED_BANS`.
3. **Тест.** Положительный и отрицательный пример в `scripts/test_markers.py`
   (на живом человеческом тексте маркер молчит).
4. **Сайт и расширение.** Правила браузерного сканера генерируются из
   `markers.py`: `python scripts/export_web_rules.py`, затем
   `python scripts/build_extension.py`. CI проверяет оба скрипта с `--check`.
5. **Счётчики.** `python scripts/bump_release.py --apply` протащит число
   признаков, запретов и категорий по README, манифестам и страницам сайта.
6. **Журнал правок.** `skills/humanizer-ru/edit-log.md` для этого не нужен:
   там накапливается фидбек на конкретные тексты (append-only, запись
   привязана к области применения). Правило, которое вы вывели из своего
   текста, а не из корпуса, дописывается внизу журнала, старые записи не
   редактируются.
7. **Гейты** из раздела выше, затем PR.

## Чеклист релиза

```bash
.venv/bin/python scripts/bump_release.py --apply vX.Y.Z
.venv/bin/python scripts/build_release_zip.py --output dist/humanizer-ru.zip .
.venv/bin/python scripts/install_smoke.py . --zip dist/humanizer-ru.zip
.venv/bin/python scripts/bump_release.py --check
```

Перед публикацией тега проверьте, что `dist/humanizer-ru.zip` приложен к
GitHub Release. После публикации ссылка
`releases/latest/download/humanizer-ru.zip` должна отдавать тот же архив.

После публикации Release (npm, PyPI, реестр MCP и ClawHub публикует CI) сверьте
живые поверхности одной командой:
`.venv/bin/python scripts/check_live_distribution.py`. Она спрашивает npm,
PyPI, реестр MCP, GitHub Release, ссылку на ZIP, сайт, карточку skills.sh,
ClawHub и HOL и сравнивает с версией в `.claude-plugin/plugin.json`. Тот же
скрипт крутится в CI раз в сутки (`live-distribution.yml`), чтобы упавшая
публикация или отставший деплой сайта не висели незамеченными.

## Правила проекта

- **Источник правды: `skills/humanizer-ru/SKILL.md`** (процедура и запреты) и
  `skills/humanizer-ru/references/catalog.md` (каталог признаков). Корневого
  `SKILL.md` больше нет (убран в v3.14.2), зеркалить ничего не нужно. Счётчики
  паттернов и версию по остальным файлам протаскивает
  `scripts/bump_release.py --apply`.
- **Никаких длинных тире в одобренных примерах.** Бан длинного тире абсолютный, линт
  ловит нарушения. Дефис с пробелами в роли тире тоже не нужен.
- **Пример не выдумывает фактов.** В паре «До/После» половина «После» не может
  содержать числа, даты, месяца, имени или названия, которых нет в «До»:
  демонстрация учит модель сильнее инструкции. Гейт `check_examples.py`.
  Пример, который намеренно показывает правку с конкретикой от автора,
  помечается в заголовке: `После (факты автора):`.
- **Пример аудита в README совпадает со сканером.** Подпись «N банов из 21» и
  строки `⛔` в README.md и README.en.md сверяются с реальным выводом
  `scan.py` на том же тексте. Меняете баны, пересоберите блок из вывода сканера.
- **Витрина живёт по своим же правилам.** README, страницы сайта в `docs/`,
  SKILL.md, команды, SECURITY.md и этот файл проходят собственные HARD BANS
  (`self_scan.py`). Цитаты плохого текста берите в ёлочки или в код: гейт их
  вырезает. Осознанная цитата бана вне кавычек помечается в строке:
  `self-scan: ok`.
- **Нет упоминаний сторонних проектов.** Находки из чужих разборов оформляются
  как «новые кейсы» и «ложные срабатывания», без ссылки на источник в коммитах,
  PR и документах.
- **Честная рамка.** Балл сканера это основание для правки, а не вердикт об
  авторстве, и инструмент не про обход детекторов.
- **Новый бан измеряется на людях.** Прежде чем добавлять конструкцию в
  `HARD_BANS`, прогоните `python eval/ainl_calibration.py` и посмотрите колонку
  human: маркер, который срабатывает на людях чаще, чем на моделях, это не
  маркер. Если он законен в отдельном регистре, его место в
  `markers.GENRE_MUTED_BANS`, а не в общем списке. Откуда берутся корпуса:
  [eval/README.md](eval/README.md#где-взять-корпуса).
- **Кандидат из шахты проходит ручную приёмку.** `eval/mine_patterns.py`
  выдаёт ранжированный список n-грамм по размеченному корпусу. Это сырьё, а не
  каталог: выхлоп нельзя отгружать пользователю без проверки человеком, который
  читает на этом языке. Обязательный шаг перед добавлением: измерить ту самую
  регулярку, которую вы собираетесь коммитить, а не n-грамму из отчёта. Разница
  бывает в разы, примеры в `eval/MINING.md`.
- **Новый паттерн идёт с доказательством.** Пример живого текста, где маркер
  встречается у нейросети и не встречается у человека. Голые ощущения не
  принимаются: проверяйте на ложные срабатывания (формальный регистр,
  осмысленные триады и т.п.).

## Eval (опционально)

Для регресс-проверки метрик достаточно детерминированного режима, как в CI:

```bash
.venv/bin/python eval/run_eval.py --baseline eval/baseline.json
git checkout -- eval/RESULTS.md   # прогон перезаписывает отчёт, верните его
```

`run_eval.py` при любом запуске пишет `eval/RESULTS.md`, поэтому после прогона
ради проверки файл нужно вернуть, иначе в PR попадёт урезанный отчёт. Эталон
`eval/baseline.json` обновляется только осознанно, флагом `--save-baseline`.

Полный прогон с детекторами, судьёй и проверкой смысла требует локальной Ollama
с `gemma3:27b` (4b слеп, не используйте):

```bash
OLLAMA_MODEL=gemma3:27b .venv/bin/python eval/run_eval.py \
  --humanized eval/corpus/humanized --detectors --judge --faithfulness
```

Такой запуск обновляет `eval/RESULTS.md` осознанно; запуск без флагов
перезапишет его урезанной версией, так не делайте.
